# Лаги приложения и лирики — отложено

Дата: 2026-09-21. Решение владельца: «Короче лаги пока что отложим, запиши в md файл, чтоб не забыть».

Задача не решена, но приостановлена. Возвращаться только по новой команде владельца. Не запрашивать новые логи и трассировки, не делать очередные оптимизации и диагностические APK по старым планам. Эта запись сама по себе не отключает существующую диагностику в коде.

## Что наблюдал владелец

- HONOR BVL-N49, Android 16; компьютера нет.
- При первых посещениях экранов и открытии лирики приложение тормозит; раньше плавность возвращалась примерно после 40–45 секунд активной работы.
- Простое ожидание без посещения вкладок не помогало. После прогрева плавность сохранялась даже при переключении песни.
- Последующие экспериментальные изменения ухудшили автоскролл лирики; владелец сообщал о лагах и после 50 секунд.
- Общая первопричина не установлена. Нельзя объявлять виновником JIT, GC, сеть, прошивку или аудиокроссфейд без доказательств.

## Что уже пробовали и откатили

1. Перенос `BoxWithConstraints` из отдельных строк в общий контейнер: на устройстве стало хуже, изменение полностью откатили. Не возвращать автоматически.
2. Замена тяжёлого состояния `Crossfade(lyrics to layoutCache)` на `LyricsCrossfadeContent` с идентичностью объекта: JVM-проверки прошли, но владелец сообщил об ухудшении. Полностью восстановили прежний `KaraokeLyricsView.kt`, удалили экспериментальный класс и его тесты. Не считать эксперимент успешным.

Во втором пункте речь об анимации смены содержимого лирики в Compose, а не об аудиокроссфейде треков. Внешний вид, растяжения, пружинную анимацию и автоскролл необходимо сохранить.

## Что показывали логи

- При открытии лирики несколько последовательных выборок main thread попадали в `Pair.hashCode → AbstractMap.hashCode → SyllableLayout.hashCode → TextLayoutResult.hashCode` внутри Compose Crossfade. Это конкретная затратная работа, но её экспериментальное устранение не решило проблему.
- Видны дорогие первые измерения и создание строк (`RowMotionData`, `calculateRowRenderData`, `BoxWithConstraints`, lookahead). В одном запуске измерение тела занимало около 103 мс, размещение 15 мс, первая отрисовка 32 мс.
- Подготовка длинной лирики занимала около 2 секунд в worker; часть этого времени UI оставался отзывчивым. Поздние лаги при автоскролле этим не объяснены.
- Есть отдельные затраты запуска: инициализация HTTP на UI до примерно 301 мс CPU, преобразование каталога на UI около 24–26 мс CPU.
- Метка `.ui` у асинхронных load/prelayout не означает непрерывную блокировку main на всё elapsed-время. Вложенные фазы нельзя суммировать; время concurrent GC не равно паузе UI. Нулевые frames в фазовом `LYRICS_OPENING` не означают отсутствие кадров.

Встроенная системная запись через Android ProfilingManager завершилась кодом 5 (`ERROR_FAILED_POST_PROCESSING`), сообщение пустое. Полноценная трассировка не получена. Скриншот и полный лог уже предоставлены; повторно просить владельца искать подробности этой ошибки не нужно.

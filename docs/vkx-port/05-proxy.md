# Обход блокировок VK X → LMG VK

Разбор сетевого прокси VK X и его порт. Источник реверса — `VKX_Fresh/jadx_out`,
дамп конфига — `VKX_Certs/vkx_remote_config_raw.json` (Firebase Remote Config
самого VK X, `templateVersion 285`, снят 02.08.2026).

## Механика

Запрос к домену VK уходит не по DNS, а на фиксированный IP: хост в URL
заменяется адресом, исходное имя возвращается заголовком `Host`.

Ключевой момент — не сама подмена, а её побочный эффект. Для IP-литерала TLS не
отправляет SNI, поэтому имя домена нигде не едет открытым текстом: узел выбирает
бэкенд по `Host`, который уже внутри шифрования. Именно поэтому подменить это
кастомным `Dns` нельзя — резолвер оставил бы SNI на месте, и DPI увидел бы
домен.

Плата за подмену — сертификат узла не совпадает с именем хоста. Отсюда весь
пиннинг: свои `X509TrustManager` и `HostnameVerifier`, принимающие цепочку по
совпадению с закреплённым сертификатом (или по подписи его ключом), а при
отсутствии совпадения падающие обратно на системную проверку.

## Карта классов VK X

| Класс | Роль | Исходное имя (из `toString`) |
|---|---|---|
| `C13079e` | интерцептор OkHttp | — |
| `AbstractC3257e` | база: редиректы, `X-Req-Hash` | — |
| `C10651e` | загрузка конфига из Firebase | — |
| `C15601e` | DI + тумблер `vkProxyEnabled` | — |
| `C10515e` | контейнер конфига | `VkConfigNetworkProxyProduct(product, version, data)` |
| `C7887e` | тело конфига | `VkConfigNetworkProxy(ip, weight, domains)` |
| `C7610e` | контейнер сертификатов | `VkConfigNetworkProxyCertificatesProduct` |
| `C3897e` | состояние «готово» | `Available(ips, ipWeights, allowedDomains, certificates)` |
| `C17103e` / `C3104e` | `FailedToLoad` / `Loading` | — |
| `C11622e` | `X509TrustManager` | — |
| `C12737e` | `HostnameVerifier` | — |
| `AbstractC12662e.ad` | PEM → `X509Certificate` | — |

Подтверждённое поведение:

- совпадение домена — `host == domain || host.endsWith(".$domain")`;
- адрес всегда первый: `AbstractC13480e.m3591interface(list)` это буквально
  `list.get(0)`, поле `weight` в клиенте не читается;
- редиректы доводятся вручную (до 20 переходов), подмена применяется заново;
- в ответ добавляется диагностический заголовок `X-Req-Hash` с хостом, которым
  запрос реально ушёл;
- **фолбэка на прямое соединение нет** — мёртвый узел означает ошибку запроса.

## Что НЕ является триггером

`mnc_for_proxy = ["255","260-07","260-08"]` в дампе есть, но в коде клиента не
читается ни разу (проверено грепом по всем исходникам). `getSimOperator()`
вызывается только в `C6803e` и заполняет поле телеметрии AppMetrica `mcc_mnc`.
Реальное включение — ручной тумблер в настройках (`C15601e.vkProxyEnabled`).

## Конфиг

Порт тянет конфиг не из Firebase, а с сервера пользователя:
`https://gsgit.org/lmg-vk/network-config.json`. Оба ключа VK
(`config_network_proxy`, `config_network_proxy_certs`) слиты в один документ,
плюс разобранный `override_api_domain` как `domain_overrides`. Документ
кэшируется в `SharedPreferences` и перечитывается по `update_delay_minutes`
(в дампе — 360 минут). Кэш переживает отсутствие сети: он мог быть загружен до
блокировки, и терять его при первой же неудаче нельзя.

Содержимое: 10 адресов `213.248.110.66..69, 83, 85..89`, 19 доменов, 4
сертификата (id 2–5) с HPKP-пинами.

## Отличия от VK X

Сделаны намеренно, все отмечены комментариями в коде:

1. **Перебор адресов.** VK X берёт первый и на этом всё. Мы идём по списку
   (отсортированному по `weight`), пока кто-то не ответит.
2. **Запасной прямой путь.** Если не ответил ни один узел, запрос уходит
   напрямую. Прокси задуман как обход блокировки, а не как единственный путь к
   сети. Повтор возможен только при перечитываемом теле — односторонний поток
   после первой попытки уже вычерпан, и тогда поведение совпадает с VK X.
3. **`domain_overrides` только на проксируемом пути.** У VK это отдельный
   эксперимент с выкаткой на 50% (`override_domain_part`); включать зеркало
   `r.vk.com` на прямом пути, который и так работает, нет причин.
4. **Редиректы доводятся вручную только для подменённых запросов.** Остальные
   отдаются наверх как есть, чтобы не дублировать чужую логику следования.
5. **Делегат проверки имени хоста — платформенный**
   (`HttpsURLConnection.getDefaultHostnameVerifier()`), а не internal-класс
   OkHttp: непроксируемые соединения должны проверяться штатно.

## Файлы порта

`app/src/main/kotlin/com/lmg/vk/network/proxy/`

- `VkProxyConfig.kt` — модели документа и состояние (`Loading` / `Available` /
  `FailedToLoad`);
- `VkProxyRepository.kt` — загрузка, кэш, тумблер, `StateFlow`;
- `VkProxyInterceptor.kt` — подмена хоста, редиректы, `X-Req-Hash`;
- `VkProxyTrust.kt` — `X509TrustManager` и `HostnameVerifier` по пинам;
- `VkProxyInstall.kt` — подключение к OkHttp-движку Ktor.

Точка включения — `LmgApplication`, `VkProxyRepository.init(this)` до создания
Ktor-клиента и `engine { config { installVkProxy() } }` в самом клиенте.
Тумблер и кнопка обновления — в настройках, раздел `NETWORK`.
